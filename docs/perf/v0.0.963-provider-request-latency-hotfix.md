# v0.0.963 provider-request latency hotfix

## Result

This lane removes two request-proportional durability operations introduced in
v0.0.962 without weakening exact provider-view storage, fail-closed prefix
validation, or persist-before-publish ordering:

- provider-view expiry maintenance remains mandatory at store open, then runs
  before a production persist only when either 64 persists or one monotonic
  hour has elapsed since the last successful sweep;
- the provider-view attempt marker and the already-batched
  `Thinking`/cache-attempt facts are committed by one journal append, in their
  original journal order and under one all-or-nothing boundary.

No timing was re-measured because this lane was explicitly constrained not to
run Cargo. The supplied interleaved A/B evidence remains the performance
baseline: v0.0.960 took 8.59--8.80 seconds for the suite, v0.0.962 took
10.70--10.78 seconds, and the delta scaled at approximately 60--75 ms per
provider request while CPU stayed flat.

## Expiry scheduling

Store open still performs an unconditional expiry sweep before the store is
published (`crates/haider-store/src/event_store.rs:1770-1799`). A
`ProviderViewSweepSchedule` now records both a persist count and an
`std::time::Instant` deadline (`crates/haider-store/src/provider_view_store.rs:29-65`).
The production persist seam consults that schedule instead of sweeping every
request (`crates/haider-store/src/event_store.rs:1823-1842`).

The count and time criteria are ORed: cleanup is due after 64 production
persists or one monotonic hour, whichever occurs first. The schedule lock is
held through cleanup so concurrent callers cannot both observe the same due
watermark. It is re-armed only after the row sweep and GC drain both succeed;
an SQL, unlink, or directory-sync failure therefore remains due and is retried
by the next production persist
(`crates/haider-store/src/provider_view_store.rs:375-468`). The seven-day
expiry policy and the `expires_at_ms <= through_ms` boundary are unchanged.

The source-sibling regression tests prove the production seam, not merely the
counter helper (`crates/haider-store/src/provider_view_store_tests.rs:1-151`):

- 63 warm persists followed by a 64-persist window containing an expired
  sentinel prove that the window performs exactly one sweep;
- a literal seven-day assertion pins the existing retention duration;
- just-before and exact-boundary sweeps prove expiry still occurs, the time
  watermark becomes due again, and a successful sweep re-arms it.

## One request-boundary journal append

Exact provider-view CAS/index persistence still completes before any matching
journal fact or provider HTTP open
(`crates/haider-core/src/actor.rs:2814-2861`). The actor now builds the
provider-view marker into the existing S6 request-attempt batch, appends the
whole batch once, then publishes the committed envelopes in order
(`crates/haider-core/src/actor.rs:2909-2931` and
`crates/haider-core/src/actor.rs:7472-7520`). The sequence remains:

1. provider-view extension `Started`;
2. provider-view extension `Completed`;
3. `RunState::Thinking`, when pending;
4. cache-attempt extension `Started`;
5. cache-attempt extension `Completed`.

If the combined append fails, none of those facts is present in the journal,
none is broadcast, and the provider is not opened. The source-sibling tests
pin the real exact-view request path, the five-event golden/render targets,
typed marker payloads with matching request ordinals, one append call,
consecutive sequence numbers, and the rejected-append journal/broadcast/watch
crash boundary (`crates/haider-core/src/actor_request_attempt_tests.rs:1-440`).

## Static operation count

The table applies to one physical provider request that produces an exact
provider view. Let `U` be the number of unique referenced CAS blocks absent at
the start of the request, `S` the number of new CAS shard directories among
those blocks, `X` the number of expired unreferenced CAS objects removed, and
`Q` the number of expiry-sweep SQLite batches (at least one when a sweep runs,
including an empty batch). Let `T` be 1 when a `Thinking` transition is pending
and 0 otherwise.

| operation on the pre-HTTP path | v0.0.962 / before | v0.0.963 ordinary request | v0.0.963 due request |
|---|---:|---:|---:|
| Expiry-sweep SQLite transaction commits | `Q` (normally 1 empty sweep) | 0 | `Q` |
| Expiry-GC unlink directory syncs | `X` | 0 | `X` |
| Provider-view GC-staging SQLite commit | 1 | 1 | 1 |
| CAS temporary-file `sync_all` calls | `U` | `U` | `U` |
| CAS shard-publication directory syncs | `U` | `U` | `U` |
| CAS-root directory syncs for new shards | `S` | `S` | `S` |
| Provider-view index SQLite commit | 1 | 1 | 1 |
| Journal append calls / journal SQLite commit boundaries | 2 | 1 | 1 |
| Journal envelopes | `4 + T` | `4 + T` | `4 + T` |
| Provider HTTP opens | 1 | 1 | 1 |

For the common no-expiry-work path (`Q = 1`, `X = 0` before the fix), this
reduces SQLite/journal commit boundaries before HTTP from five to three:
expiry sweep + GC staging + provider-view index + two journal appends becomes
GC staging + provider-view index + one journal append. A due request has four
such boundaries when its sweep needs one batch. SQLite uses WAL
`synchronous=NORMAL`, so these are transaction/durability boundaries rather
than a claim that every commit issues a distinct physical filesystem fsync.
The explicit CAS file and directory sync counts are unchanged.

## 0c crash-consistency judgment

No CAS directory sync was coalesced and no provider-view block was inlined.
The existing Unix publication order is deliberately conservative:

1. expected content addresses are staged in the GC table and committed before
   filesystem writes (`crates/haider-store/src/provider_view_store.rs:108-120`
   and `crates/haider-store/src/provider_view_store.rs:309-328`);
2. each new object is written to a temporary file and `sync_all` completes
   before hard-link publication (`crates/haider-store/src/cas.rs:314-351`);
3. temporary removal and the final hard-link directory entry are followed by
   a shard-directory sync (`crates/haider-store/src/cas.rs:1001-1008`), with a
   root-directory sync when a shard is first created
   (`crates/haider-store/src/cas.rs:329-334`);
4. only afterward does the provider-view index transaction publish the durable
   cursor and remove the expected addresses from the GC queue
   (`crates/haider-store/src/provider_view_store.rs:121-214`);
5. store-open and due sweeps drain any staged, unreferenced GC entries
   (`crates/haider-store/src/provider_view_store.rs:412-503`).

That order demonstrates why removing a current Unix sync would require a new
durability proof. More importantly, the CAS routes directory synchronization
through `haider_platform::sync_directory`
(`crates/haider-store/src/cas.rs:1019-1022`), whose Windows implementation is
currently a no-op (`crates/haider-platform/src/fs.rs:85-88`). Therefore a
cross-platform proof that a published content address cannot survive while its
bytes do not was not available in this lane. Under the explicit 0c rule, the
optimization was skipped rather than weakening or overstating crash safety.
