# v0.0.967 group commit and provider-view Barrier report

## Outcome

The profile committer now accepts ordinary/worker appends, receipt-backed
`session.create` and `turn.submit` mutations, and hook-outbox acknowledgements.
Mixed groups retain one savepoint per logical request and one outer SQLite
transaction. A semantic failure rolls back only its savepoint. A fatal store
failure rolls back the whole group.

There is no intentional batching delay on a mutation. The committer takes the
first request and drains the requests already waiting, while the wider request
coverage makes receipt-backed mutations and acknowledgements eligible for the
same physical transaction. Standalone hook acknowledgements retain their
direct transaction; an acknowledgement uses the committer opportunistically
while a mutation is already admitted.

A bounded scheduler-yield batching window was implemented and measured under
confirmed concurrency, then rejected. It formed multi-request groups, but
reduced throughput. A lone request did not enter that window, so the experiment
did not trade interactive latency for the cohort result. The final design has
no timer, sleep, or scheduler yield.

The provider-view CAS group fence changes from `SyncPolicy::Full` to
`SyncPolicy::Barrier` on Apple. Unsupported Apple barriers fail closed rather
than degrading to `Plain`. The downgrade is deliberately provider-view-only:
generic `Cas::put_batch` (including checkpoint preimages) retains its trailing
`Full` fence and persistence-at-return contract.

## Wall and fence measurement

Host: arm64, macOS 26.6.2 (25G83), APFS. Both revisions were compiled with the
release-gate environment and `CARGO_INCREMENTAL=0 CARGO_PROFILE_DEV_DEBUG=0`.
The before source was `61c1ab3`; the after source was this lane. An identical
temporary real-daemon/RPC harness used the real Anthropic provider-view
renderer and a scripted stream boundary. Each sample used a fresh profile and
workspace. Revisions alternated order on successive samples.

- Single mode: one ordinary no-tool turn, one physical provider request.
- Multi mode: one turn with five sequential no-output `process_exec` calls and
  continuations, six physical provider requests.
- `n=20` per revision and mode. Values are turn-submit through client-visible
  terminal event; setup and shutdown are outside the interval.

| Workload | Before p50 (IQR) | After p50 (IQR) | Delta | Physical fences |
|---|---:|---:|---:|---:|
| Single turn | 45.393 ms (40.132–75.761) | 54.309 ms (41.024–81.790) | +8.917 ms (+19.6%) | 1 → 1 |
| Five-tool turn | 271.014 ms (230.853–374.981) | 356.721 ms (314.774–442.287) | +85.707 ms (+31.6%) | 6 → 6 |

This is an honest negative whole-turn result. The distributions were highly
sensitive to host load across cohorts. A same-fence isolation run (Barrier on
both sides, `n=20`) measured the committer change itself at 42.030 → 40.815 ms
for the single turn and 235.132 → 245.793 ms for the five-tool turn. Therefore
the experiment does not support a whole-turn speedup claim. Both workloads are
sequential and therefore exercise the final delay-free committer policy.

The latency/throughput trade was measured separately with four no-tool turns
released simultaneously through four sessions. Samples alternated the base
and experimental revisions; `n=20` cohorts used fresh profiles. The
experimental revision added one scheduler yield only after more than one
receipt mutation had registered, so a single interactive mutation still paid
no delay.

| Four-turn cohort | Base | One-yield batching experiment | Delta |
|---|---:|---:|---:|
| Wall p50 (IQR) | 205.903 ms (200.686–211.938) | 218.127 ms (213.186–226.500) | +12.225 ms (+5.9%) |
| Throughput at p50 | 19.43 turns/s | 18.34 turns/s | −5.6% |
| Total WAL commits, median | 63 | 63 | 0 |
| Multi-request committer groups, median | 0 | 1 | +1 |

The committer counters are not directly comparable as commit counts: the base
committer observed 28 ordinary append requests, while the experiment observed
37 receipt/append/ack requests because this lane extends its coverage. The WAL
commit-marker count is the comparable total and did not improve. Forming one
mixed group merely shifted which requests shared transactions while scheduler
work increased cohort wall time. The batching delay is therefore not shipped.

An interleaved 101-sample filesystem microbenchmark isolated the exact trailing
directory operation:

| Fence | p50 | p95 |
|---|---:|---:|
| `F_FULLFSYNC` | 4.611 ms | 9.861 ms |
| `F_BARRIERFSYNC` | 2.999 ms | 9.713 ms |

Barrier reduced the isolated p50 by 1.612 ms (35.0%). That result is not used
as a substitute for the negative whole-turn result above.

## Why Barrier is sufficient for this fence

The provider-view operation has two phases on one profile device:

1. publish every immutable CAS file and directory entry, then plain-`fsync`
   each affected file and directory;
2. publish the SQLite CAS index and request-attempt journal facts in one
   transaction.

The current macOS `fcntl(2)` manual defines `F_BARRIERFSYNC` as `fsync` plus a
device barrier. I/O already flushed with `fsync` on the same device is
guaranteed to persist before I/O following the barrier. It explicitly gives
the same two-phase recipe: fsync every phase-one descriptor, issue one barrier,
then perform phase two. Descendance from one profile path is not enough to
prove this invariant because a nested mount could cross devices. Store startup
therefore compares the Apple device ids of the profile root (which directly
contains `store.sqlite`) and `provider-view-cas`, rejecting a mismatch. With
that same-device invariant enforced, this is exactly the required ordering
boundary.

After a successful Barrier, these statements remain true across power loss:

- A surviving provider-view index/request-attempt transaction cannot reference
  a CAS block or directory entry that failed to survive. Phase two cannot be
  persisted without phase one.
- The provider-view index and its matching request-attempt facts retain their
  existing SQLite transaction atomicity.
- Exact replay and fork-from-prompt never observe a surviving durable index
  whose referenced CAS blocks are absent solely because of write reordering.

This stronger statement stops being true:

- Return from the CAS fence no longer means the phase-one blocks themselves
  are strongly expected to be on permanent media at that instant. A power cut
  may lose the complete newest phase: blocks plus the later index/attempt
  transaction. Under Full, the blocks were strongly expected to persist when
  the fence returned, even if the later WAL transaction was lost, leaving
  unreferenced blocks.

The journal uses WAL with `synchronous=NORMAL` and `fullfsync=0`; it never had a
power-cut promise for the newest commit window. Barrier therefore weakens the
standalone persistence expectation for pre-index CAS blocks, not the
surviving-index referential-integrity guarantee.

## Why the fence remains per physical request

The request-attempt facts are required before the provider HTTP request opens.
Moving the barrier and index transaction to turn completion creates an invalid
choice:

- commit each request's index/attempt before the end-of-turn barrier, allowing
  a power cut to preserve an index whose blocks have not crossed the ordering
  boundary; or
- defer the index/attempt facts until turn completion, so a crash during a
  tool continuation loses evidence for physical provider requests that already
  occurred and breaks exact replay/fork evidence.

The legitimate boundary is therefore each physical provider request, not each
turn. The measured five-tool turn stays at six barriers; collapsing it to one
would weaken the named contract.
