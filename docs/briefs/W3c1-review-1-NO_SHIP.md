## 2. Findings

### P1

1. **P1 — A dispatched effect can append `Unknown` after `RunState::Cancelled`.**  
   Core closes items and commits Cancelled first ([actor.rs:1701](/Users/rizzist/haider-run/haider-w3c/crates/haider-core/src/actor.rs:1701)); only after the outcome does the supervisor close the dispatcher ([worker.rs:563](/Users/rizzist/haider-run/haider-w3c/crates/haider-daemon/src/worker.rs:563)). `EffectBroker::close` then reconciles held dispatches to Unknown ([broker.rs:735](/Users/rizzist/haider-run/haider-w3c/crates/haider-tools/src/broker.rs:735)), through a run-scoped journal envelope ([worker.rs:1450](/Users/rizzist/haider-run/haider-w3c/crates/haider-daemon/src/worker.rs:1450)). Concrete schedule: tool reaches Dispatched, cancel while held, core appends Cancelled, broker close appends Unknown afterward.

2. **P1 — Cancellation committed during `start_turn` can still start the provider.**  
   The supervisor awaits `start_turn` outside its cancellation select ([worker.rs:478](/Users/rizzist/haider-run/haider-w3c/crates/haider-daemon/src/worker.rs:478)). `start_turn` resolves the provider and submits the harness without rereading durable run state ([worker.rs:838](/Users/rizzist/haider-run/haider-w3c/crates/haider-daemon/src/worker.rs:838)). Concrete schedule: ProviderFactory blocks; wire commits Cancelling; release factory; provider request begins before the supervisor processes the wake.

3. **P1 — Actor-ordered cancellation can be followed by Done.**  
   The hub commits Cancelling and asynchronously wakes the supervisor ([actor.rs:137](/Users/rizzist/haider-run/haider-w3c/crates/haider-daemon/src/session_hub/actor.rs:137)); a subsequent current-lease WorkerAppend is accepted without validating the run transition ([actor.rs:178](/Users/rizzist/haider-run/haider-w3c/crates/haider-daemon/src/session_hub/actor.rs:178)). ### P3

12. **P3 — Menu answers do not share the global command-ID namespace.**  
    Create/submit/cancel use `command_receipts`; menu answers consult only `menu_resolutions` ([event_store.rs:1504](/Users/rizzist/haider-run/haider-w3c/crates/haider-store/src/event_store.rs:1504)). The same command ID can therefore successfully drive a turn command and a menu answer.

13. **P3 — Distinct cancel command IDs append duplicate Cancelling states.**  
    Any nonterminal state, including already-Cancelling, takes the append branch ([event_store.rs:782](/Users/rizzist/haider-run/haider-w3c/crates/haider-store/src/event_store.rs:782)). This is bounded durable noise rather than a terminal-safety failure.

Receipt discipline otherwise holds: create/submit/cancel claim, mutation, and receipt finalization occur in one `BEGIN IMMEDIATE` transaction, so process death cannot durably leave “claimed but not executed”; committed-response loss replays across restart. Store-level concurrent submit is pinned. A true simultaneous two-connection wire submit is not directly tested.

Recovery order is sound for the tested cases: effects reconcile first, then all prior-generation turns, then hub/manager installation, and only afterward endpoint binding. Consequently an immediate wire attach cannot race startup recovery. The mixed multi-session state is not covered as one fixture.

## Fable design report

## 1. DESIGN FINDINGS\n\n**Lens summaries (evidence in the numbered findings):**\n- **WorkerManager vs R1**: shape is right. One lazy supervisor per session, one `JoinSet`, nothing detached; single kill chain (manager abort → JoinSet drop → supervisor abort → `ActiveTurn`/`AbortOnDropTask` drop → actor abort). It is *not* a second competing idiom vs W3b1's `OwnedTasks`: the fence-before-abort discipline lives only where uncancellable store writes happen (the hub), and workers reach the store only through the fenced hub actor, so they don't need their own fence — that's coherent layering, not drift. Hub-actor purity holds by shape (`actor.rs:1-19`: every in-arm await is a store call; `Register` has none).\n- **Receipt system**: genuinely ONE discipline. One law site (`event_store.rs:392-400` on `session_create_receipt`), one shared `claim_pending_receipt`/`finalize_command_receipt`/`lookup_command_response`, identical unfenced-preflight-then-fenced-transaction composition in `rpc.rs` for all three methods. The claim/execute/commit lifecycle is single-transaction in W3c1 (pending state never externally observable) but the helpers take `&Transaction`, so W3c2's two-transaction login flow adopts them verbatim.\n- **Module split**: charters hold. actor.rs, replay.rs, worker.rs, turn_recovery.rs each contain only what their charter permits; the one charter claim the code can break is D2-2 below. rpc.rs's direct `hub.inner.store` reads are sanctioned (reads bypass the actor by design).\n- **Recovery**: same phase machine as C4a, extended — effects reconcile → turn reduction → hub/manager → feed recovered work → bind → Ready (`runtime.rs:229-336`), with effects-before-turns matching the risk register. Laws are careful-code-plus-charter-plus-manifest, not by-construction — acceptable, except the D1 hole.\n- **Provider seam**: `spawn_with_dependencies` is the production entry; tests swap only the factory (`support/mod.rs:45-51`), so the FakeProvider seam IS the production seam. `ProviderFactory::resolve_for_turn` per logical turn means /login swaps credentials with zero worker changes. R6's stream-ownership requirement landed (`ProviderStream` abort-on-drop + `response_open_timeout`).\n\n### D1 — must fix before merge\n\n**D1-1. A poison recovered-work item is daemon-fatal and permanent — one bad session becomes a startup crash-loop.** `runtime.rs:286-305` treats ANY error while feeding recovered work as total teardown + `Err`. `supervisor_for` (`worker.rs:395-401`) errors on a session with no typed metadata (\"legacy session has no live-worker metadata\"), and `turn_recovery.rs:110-123` re-enqueues prior-generation `Queued` runs with no runnability check and never terminalizes them. Reachable chain: a legacy/CLI-seeded session (ordinary append auto-creates `{}` metadata rows; the standalone CLI writes turns directly) holds a prior-generation `Queued` run → every daemon start recovers it → `supervisor_for` fails → startup aborts → next start repeats **forever**; nothing ever terminalizes the run. Worse, a live `turn.submit` against such a session is durably ACCEPTED (`accept_turn` checks only `require_session`, `event_store.rs:628`) before `supervisor_for` fails — so the wire itself can plant the poison run. The W3c2 variant: a parked `request_input` checkpoint whose credentials were revoked fails `start_turn` pre-Ready (`worker.rs:499-512`), aborts startup once, terminalizes the run via `append_failure` **without closing its open menu** (compare `terminalize_interrupted`, `turn_recovery.rs:318-327`) — leaving a permanently orphaned open menu.\n*Design argument*: this conflates \"recovery of durable truth\" (fatal on failure — correct, C4a discipline) with \"resumption of runnable work\" (must degrade per-run). R5's own rule is *terminalize what cannot resume*; the daemon dying instead violates it. Fix by construction: (a) acceptance must guarantee what the supervisor needs — `accept_turn` requires typed metadata, so a legacy session gets a correlated `invalid_argument` instead of a post-commit wedge; (b) per-item recovery-feed failure terminalizes that run (RunFailed/Errored + menu `RecoveryInterrupted` + `Idle{interrupted:true}`) and startup continues.\n\n### D2 — fix or ledger before merge\n\n**D2-1. R6 deviation: provider `retry_after_ms` clamped to the 2 s jitter ceiling** (`actor.rs:1186-1189`, `:1222`; clean-code finding 1). The daemon retries EARLIER than the provider asked — R6 intends the ceiling for the jitter formula only. Documented as KNOWN LIMITATION but neither fixed nor ledgered. Must be resolved before W3c2 puts real 429 traffic on it: honor `retry_after_ms` up to a real provider-respect cap (or terminalize when it exceeds the cap), keep the 2 s ceiling for computed jitter only.\n\n**D2-2. Manager submit path has cross-session head-of-line blocking, and it breaks rpc.rs's own charter.** `run_manager` awaits `supervisor.send(...)` inline (`worker.rs:329-333`); a full 64-slot supervisor queue blocks the manager loop — and every other session's submit — while `admit_pending` drains at `durable_runs` O(journal) cost per item (`worker.rs:647`). `rpc.rs` awaits `worker_manager().submit()` inline on the connection task (`rpc.rs:286`), whose charter promises \"the longest await is one store transaction or one workspace spawn_blocking\" (`rpc.rs:10-12`). The risk register demands bounded queues yield *typed overload*, not stalls. Cheap fix: `try_send` on the supervisor channel with `Busy` (rpc already maps `Busy` → `overloaded`, `rpc.rs:391`); the durable Queued pair is already the overflow buffer by design.\n\n**D2-3. `Idle { interrupted }` semantics have no law site and no pin** (clean-code finding 6). Live cancel settles `false`, drain/recovery settle `true` — coherent (\"daemon stopped the work\" vs \"work concluded\"), but the flag is chosen at three scattered call sites (`worker.rs:574-575` stamps the `stopping` flag — which also stamps `true` on a turn that *completed naturally* during drain, a semantic fuzz worth deciding; `turn_recovery.rs:336-338`; `worker.rs:669`), while the settle law (`event_store.rs:830-836`) and `SessionState::Idle` docs are silent. State it once on `settle_session_idle` or the protocol variant, pin with one test.\n\n**D2-4. Store fence-vs-replay asymmetry is a documented trap with no ledger row** (clean-code finding 2). `resolve_menu` does replay-before-fence *inside* the store; `accept_turn`/`cancel_turn` do fence-before-replay and delegate cross-restart replay to the wire layer's unfenced preflight (`event_store.rs:588-595`, `:731-734`).
