## The headline: both lenses independently reproduced the SAME bug

**Double attach on every gap / Lagged / reconnect** (codex P1-3 == design D1-1). M3.2 declared "ONE reattach authority", but the in-flight `attaching` latch lives in the CALLER (`sync_selection`) while FOUR sites emit `Attach`; `run_live`'s loop tail then unconditionally calls `sync_selection`, which sees the session unattached and attaches again. Measured 2 attaches per 1 detach on all three paths. The daemon charges a slot per `session.attach` with no dedup and the driver keeps only the last attachment id, so the orphan is never detached yet still accepts events; 16 gaps wedge the connection at `max_attachments_per_connection`, after which retryable `overloaded` makes `sync_selection` retry forever. Fix shape (design): move the latch INTO `ensure_attached`, the single emitter, so the invariant is unrepresentable to break.

## Adjudications

### Declared deviations

- **`DraftKey::Session(UiGeneration)` — sound design, rejected as shipped.** A transient surface generation is preferable to a wire coordinate for stale-draft protection. The argument depends on generations never being reworn; `/reset` disproves that premise. It becomes acceptable once replacement seeds receive fresh generations while retaining stable demo `SessionId`s.

- **Removing `session.read` — acceptable architecture, acceptance not met.** Selection-triggered attach/replay can be the sole reading path and avoids a second projector. That argument is sound in principle. It fails operationally here because sessions beyond the first three cannot be selected and the attach/replay transport can lose opening or final events.
