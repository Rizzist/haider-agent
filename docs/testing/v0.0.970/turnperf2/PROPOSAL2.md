## 3. A 70 ms path

There is **no credible path from the canonical 124 ms cold one-shot median to below 70 ms without changing the spawn/accounting mode**.

A discounted implementation portfolio comprising R2-03 through R2-23 is expected to remove only about **10–14 ms non-additively**, giving a best credible ordinary cold median of approximately **110–114 ms**. An optimistic edge near 104 ms is not credible enough to plan against after round 1’s 2–4× estimation error.

Adding R2-02, the full in-process daemon, yields approximately **102–108 ms** after overlap with the same portfolio. It still performs store open, recovery, initialization, the turn, and ordered drain, and it weakens lifecycle semantics; it does not create a 70 ms path.

The minimal credible path is therefore:

| order | row | discounted credited saving | running median |
|---:|---|---:|---:|
| 0 | Canonical 968 one-shot baseline | — | **124 ms** |
| 1 | R2-01 explicit already-running resident-profile service | **60 ms** credited versus the measured 67.3 ms gap | **64 ms planning estimate** |

The directly measured equivalent is **56.7 ms**, because R2-01 changes the timed operation to the existing warm-service class. Safe warm-path rows could plausibly lower that to **53–55 ms**, but they are unnecessary to cross 70.

Best achievable medians:

- **Ordinary spawned daemon:** approximately **110–114 ms** credible.
- **Cold in-process full daemon:** approximately **102–108 ms**, still above 70 and not fully contract-equivalent.
- **Already-running resident daemon:** **56.7 ms measured**, approximately **53–55 ms** after conservative warm-path improvements.

The resident result must never replace or obscure the canonical setup→stop one-shot score or CPU total.
